GIFdroid Comparative Report

How GIFdroid breaks on HHV compared to SRV

This report summarizes the behavior of GIFdroid on handheld video (hhv) versus screen recording (srv) using the extracted results in analysis/gifdroid_data.json. The headline result is not a large raw failure-rate gap. The deeper issue is that hhv completes with substantially worse reconstruction quality: more spurious keyframes, weaker GUI mapping, shallower traces, and dramatically worse runtime.

Dataset date: 2026-03-23 Runs analyzed: 44 Apps present in JSON: 8 of 10 Missing apps: DeadHash, Pomodorot

Executive Summary

If you only look at pipeline_complete, hhv and srv appear similar. That metric hides the actual limitation. GIFdroid is much less robust on handheld recordings, where the pipeline often still finishes but reconstructs a poorer execution trace from noisier visual evidence.

Completion counts are similar

On the surface, HHV does not fail much more often than SRV. Completion alone is not a strong enough metric to judge practical utility.

Quality gap is the real story

HHV systematically lowers mapping confidence, reduces unique mapped states, and weakens downstream trace quality.

Handheld robustness is the limitation

GIFdroid appears sensitive to camera motion, framing changes, blur, and compression noise. Those factors distort the visual signal before the trace search even begins.

Core Trends

1. HHV over-detects keyframes

The strongest recurring pattern is excessive keyframe detection on handheld video. In several apps, HHV reports many more state changes than SRV even when the actual UI flow should be similar.

2. GUI mapping collapses

After those extra HHV keyframes are generated, many of them map back to the same screenshot. This means the added keyframes are usually not informative state transitions.

3. Trace quality drops

Lower mapping quality leads to lower LCS and weaker recovered traces. In practice, HHV completes more often than it succeeds meaningfully.

4. Runtime can explode

Noisy visual inputs create a much heavier search problem. The most extreme example is AntennaPod, where HHV takes roughly 26 times longer than SRV.

Key global ratios
  • Average LCS: HHV 1.07 vs SRV 2.32
  • Average trace length: HHV 5.27 vs SRV 7.47
  • Median total time: HHV 257s vs SRV 149s
  • Mean unique screens per keyframe: HHV 0.064 vs SRV 0.565
Interpretation
  • HHV introduces visual instability that keyframe detection treats as app-state changes.
  • The mapping stage then compresses those noisy frames into repeated screenshot matches.
  • The trace finder receives a low-information target sequence and recovers shallower paths.
  • Even “successful” HHV runs therefore often produce weaker replay traces than SRV.

Observed Failure Modes

The incomplete runs reveal that GIFdroid does not fail in only one way. The logs suggest a mix of true runtime failures, stalled trace search, and analysis-extraction inconsistencies.

Hard early termination

In LuxAlarm utg02 srv, the log stops right after frame decoding in Step 1. The JSON has no meaningful Step 2 or Step 3 outputs, which points to a real pipeline failure during early processing.

Trace search stall after mapping

In LuxAlarm utg02 hhv and LuxAlarm utg03 srv, keyframe detection and mapping finish, but the run stops after the UTG is read. That suggests trace search can fail or hang even when upstream stages succeed.

Parser or extraction inconsistency

In PortAuthority utg03 hhv, the raw log clearly says the pipeline completed, but the JSON marks the run incomplete and drops final metrics. At least one observed “failure” is therefore a report-generation issue.

LuxAlarm HHV failure signature
  • 11 keyframes detected
  • All 11 mapped to the same screen index 7
  • Trace search begins with a repeated target sequence
  • Run stops after UTG load with no recovered trace
Why this matters
  • Not every bad run is a crash; many are low-information reconstructions.
  • Repeated-screen mapping is a strong predictor of downstream trace weakness.
  • Some JSON failure counts should be treated carefully because of parser inconsistencies.

GIFdroid Limitations Exposed by HHV

Input robustness limitation

GIFdroid appears highly sensitive to the visual instability of handheld capture. Camera movement, reframing, compression variation, blur, and lighting differences likely create enough local change to trigger spurious keyframes.

Mapping brittleness

The GUI-mapping stage struggles to preserve state diversity on HHV inputs. Even when many keyframes are detected, they frequently collapse back to one screenshot match with modest confidence scores.

Trace dependency on clean sequences

The trace finder depends on a meaningful mapped sequence. Once the sequence becomes repetitive or low-confidence, the search either returns very shallow traces or fails to complete.

Performance limitation

Runtime becomes impractical on some HHV runs. That makes the system fragile not just in correctness terms, but also in scalability and operational cost.

The main limitation is not that HHV always crashes. It is that HHV frequently converts GIFdroid from a trace-recovery tool into a noisy, low-fidelity approximation of the app’s execution.

Bottom Line

If the question is “Does HHV fail more than SRV?”, the strict completion-rate answer is: not by much. If the question is “Which mode gives a usable reconstruction?”, the answer is much clearer: SRV is consistently more reliable, more informative, and far more efficient.

  • HHV is not dramatically worse in raw completion count.
  • HHV is much worse in reconstruction quality.
  • HHV generates more spurious keyframes and fewer distinct mapped states.
  • HHV leads to lower LCS, shorter traces, and much higher runtime.
  • At least one reported failure is caused by analysis extraction, not GIFdroid itself.
