TOP 10 REASONS FOR STEP FAILURE IN DEVICE AUTOMATION
====================================================

Based on analysis of 14 apps × 2 modes = 28 automation runs

================================================================================
1. SETUP WIZARD/FIRST-TIME LAUNCH SCREENS
================================================================================
Frequency: ~18% of all failures
Impact: Complete task blockage (0% reproduction in affected runs)

Description: 
Automation encounters app setup flows (onboarding, permissions, configuration 
wizards) that are absent from memory recordings. Memory assumes pre-configured 
app state.

Reference Runs:
- homeraudioplayer HHV (0%): Steps 1-4 stuck in setup wizard 
  (Sample books → Next → Done loop)
- homeraudioplayer SRV (0%): Steps 1-4 identical setup wizard stall
- adaway HHV (20%): Steps 1-7 consumed by VPN setup wizard, never reached 
  whitelist task
- adaway SRV (55%): Steps 1-7 setup (VPN connection, notifications), 
  partial recovery

Root Cause: 
Memory recorded from already-launched app; automation starts with fresh 
install state.

================================================================================
2. ANALOG/COMPLEX CONTROL INTERACTION FAILURES
================================================================================
Frequency: ~15% of all failures
Impact: Task stall or wrong action (11-40% reproduction)

Description: 
LLM struggles with non-standard UI controls: analog clocks, drag sliders, 
custom pickers. Taps when should drag, repeats same tap, or taps wrong element.

Reference Runs:
- luxalarm HHV (22%): Steps 3-5 analog clock (tap "1", tap "25", then 
  repeated "25" tap × 4 = stall)
- luxalarm SRV (11%): Step 4 tapped digital display "13" instead of dragging 
  minute slider
- homemedkit HHV (40%): Step 7 APR month picker (repeated tap × 4 = stall)
- newpipe HHV (55%): Steps 7-9 tapped "1x" button × 3 (146s delay), dialog 
  never opened

Root Cause: 
LLM trained on standard tap/swipe; analog controls require spatial reasoning 
or drag gestures not well-represented in training.

================================================================================
3. DIALOG CONFIRMATION MISSING
================================================================================
Frequency: ~14% of all failures
Impact: Partial task completion (40-80% reproduction)

Description: 
Automation completes primary action but fails to confirm follow-up dialog 
(OK, Save, Confirm, Continue buttons). Task appears done but state not 
committed.

Reference Runs:
- bily HHV (45%): Step 5 tapped Reset but never confirmed dialog 
  (stuck at step 5)
- bily SRV (40%): Step 3 tapped Reset, stalled before confirmation
- brethap HHV (80%): Step 4 reached Clear All menu but never tapped 
  Continue button
- homemedkit HHV (40%): Step 5 tapped Save in group dialog (not in memory), 
  wrong confirmation
- newpipe HHV (55%): Steps 6, 9 missing OK button taps after speed changes

Root Cause: 
LLM treats action as complete without recognizing required confirmation step; 
dialogs not detected in UI tree or misclassified.

================================================================================
4. SCROLL/SEARCH NAVIGATION FAILURES
================================================================================
Frequency: ~12% of all failures
Impact: Task incompletion (30-35% reproduction)

Description: 
Automation attempts to scroll/search for UI element but never finds it. 
Repeats scroll action 4+ times in same direction without success.

Reference Runs:
- binaryeye HHV (35%): Steps 5-8 scrolled down × 4 looking for "Go back 
  after copying" toggle (never found)
- binaryeye SRV (30%): Steps 5-8 identical scroll × 4 failure pattern
- antennapod SRV (60%): Steps 7-8 confused navigation (back tap, re-tap menu) 
  instead of scrolling to Downloads

Root Cause: 
UI element off-screen or in different settings category; LLM scroll 
direction/distance calculation incorrect; stall detection triggers after 
4 identical attempts.

================================================================================
5. WRONG NAVIGATION PATH SELECTION
================================================================================
Frequency: ~10% of all failures
Impact: Divergent flow, task abandoned (20-40% reproduction)

Description: 
Multiple navigation options available; LLM chooses wrong path (wrong menu 
item, wrong tab, wrong icon). Often reaches similar-looking but incorrect 
screen.

Reference Runs:
- bakerspercentagecalculator HHV (40%): Step 3 tapped Gallery (QR scanner) 
  instead of file picker
- adaway HHV (20%): Step 8 reached HostsSourcesActivity instead of 
  "Your lists" menu
- adaway SRV (55%): Step 9 tapped "Allowed" card directly instead of 
  menu → "Your lists" → "Allowed" tab
- luxalarm SRV (11%): Step 1 tapped teal alarm icon instead of + FAB 
  (corrected in step 2)

Root Cause: 
Multiple UI elements with similar labels/icons; LLM picks based on visual 
similarity without semantic understanding of task flow.

================================================================================
6. PERMISSIONS/SYSTEM DIALOGS NOT IN MEMORY
================================================================================
Frequency: ~10% of all failures
Impact: Extra steps, delays (adds 1-3 steps per run)

Description: 
Android system dialogs (VPN connection, notifications, file access) appear 
in automation but not in memory. Not blocking failures but consume step 
budget.

Reference Runs:
- jigsaw HHV (0%): Steps 2-5 file access toggle repeated × 4 
  (blocked entire task)
- newpipe HHV (55%): Steps 1-2 "Don't allow" + OK dialogs (handled correctly 
  but not in memory)
- newpipe SRV (57%): Steps 1-3 permissions + Android dialog 
  (handled correctly)
- homemedkit HHV (40%): Step 0 (unlabeled) grant permission dialog

Root Cause: 
Memory recordings skip system dialogs (user already granted permissions); 
automation with fresh install hits every permission request.

================================================================================
7. TASK INCOMPLETENESS (STEP BUDGET EXHAUSTION)
================================================================================
Frequency: ~9% of all failures
Impact: Partial completion (40-60% reproduction)

Description: 
Automation completes first N steps correctly but runs out of steps before 
finishing task. Often 10-step limit reached on tasks requiring 12-15 steps.

Reference Runs:
- adaway SRV (55%): Step 10 reached + FAB, never typed "abc.com" 
  (steps 1-10 consumed by setup+navigation)
- bloodpressuremonitor HHV (40%): Step 5 entered first record data, never 
  saved (memory shows 2 records + statistics)
- antennapod SRV (60%): Step 10 reached Playback settings toggle, never 
  reached Downloads section
- brethap SRV (45%): Step 4 completed 1.5 sessions, never reached 
  menu → clear all

Root Cause: 
Fixed 10-step automation limit; tasks with setup overhead + main flow exceed 
budget. Memory shows complete flow but automation truncates.

================================================================================
8. STATE MISMATCH (APP ALREADY LAUNCHED VS FRESH START)
================================================================================
Frequency: ~8% of all failures
Impact: Divergent initial steps (affects reproduction from step 1)

Description: 
Memory starts mid-session (app already open, user on specific screen); 
automation starts from app icon or Play Store. Different starting states 
lead to different step sequences.

Reference Runs:
- bakerspercentagecalculator SRV (100%): Memory step 1 = "Launch" but 
  already in app; automation step 1 = + FAB (skipped launch)
- bloodpressuremonitor SRV (100%): Memory step 1 = statistics screen 
  (already navigated); automation starts from home
- jigsaw HHV (0%): Memory step 1 = "Tap Open button on Play Store"; 
  automation already past that
- jigsaw SRV (N/A): Memory step 1 = "Tap Jigsaw app icon" 
  (home screen launch)

Root Cause: 
Memory recording starts after app launch or mid-task; automation has no 
context of prior state. Not always blocking but creates step offset.

================================================================================
9. CONTROL IDENTIFICATION/LABELING CONFUSION
================================================================================
Frequency: ~7% of all failures
Impact: Wrong action or repeated failed taps (reduces reproduction by 10-30%)

Description: 
LLM misidentifies UI element (confuses similar icons, wrong button label, 
or taps placeholder text instead of input field).

Reference Runs:
- newpipe HHV (55%): Step 8 tapped "1x" speed button (correct) but dialog 
  didn't open; steps 7-9 repeated tap × 3
- newpipe SRV (57%): Steps 8-9 tapped "1x" then "Queue" button (confused 
  with list icon for tempo dialog)
- homemedkit HHV (40%): Step 5 tapped Save button in group dialog (not in 
  memory flow; dialog should auto-close)
- antennapod HHV (83%): Step 3 tapped Show suggestions (extra step not in 
  memory)

Root Cause: 
LLM visual grounding weak on small icons or ambiguous labels; accessibility 
tree may have incomplete/generic labels.

================================================================================
10. RECOVERY/ERROR HANDLING FAILURES
================================================================================
Frequency: ~5% of all failures
Impact: Stall after error (automation stops instead of retrying)

Description: 
Automation encounters unexpected state (empty field, wrong screen, error 
message) and either repeats same action or terminates without trying 
alternative approach.

Reference Runs:
- batterytemperaturedisplay SRV (75%): Step 2 tapped Start (error: empty 
  duration), step 3 tapped duration input (recovered), step 5 retried 
  Start (success)
- jigsaw HHV (0%): Steps 2-5 repeated permission toggle × 4, LLM 
  self-terminated (continue=false) at step 5
- binaryeye HHV/SRV (30-35%): Both modes scrolled × 4 without finding 
  toggle, stall detection triggered (no alternative navigation attempted)
- luxalarm HHV (22%): Steps 4-5 repeated minute tap × 4 (stall detection; 
  no attempt to drag instead)

Root Cause: 
Stall detection (4 repeated actions) triggers termination; LLM doesn't try 
alternative strategies (drag vs tap, different navigation path, skip step).

TREND ANALYSIS
================================================================================

FAILURE SEVERITY BY CATEGORY
-----------------------------

High Impact (blocks task completely, 0-30% reproduction):
  - Setup/Wizard Screens: 18%
  - Analog Control Issues: 15%
  - Wrong Navigation Path: 10%
  TOTAL: 43% of failures

Medium Impact (partial completion, 40-70% reproduction):
  - Dialog Confirmation Missing: 14%
  - Scroll/Search Failures: 12%
  - Step Budget Exhaustion: 9%
  - State Mismatch: 8%
  TOTAL: 43% of failures

Low Impact (annoyances, 70-90% reproduction):
  - Permissions Not in Memory: 10%
  - Control Identification: 7%
  - Recovery Failures: 5%
  TOTAL: 14% of failures


TEMPORAL TREND (Setup → Execution → Completion)
------------------------------------------------

PHASE 1: APP SETUP (Steps 1-3)
Failures:
  • Setup wizards (18%)
  • Permissions dialogs (10%)
  • State mismatch (8%)
  Total: 36% of failures occur here

PHASE 2: TASK EXECUTION (Steps 4-7)
Failures:
  • Analog controls (15%)
  • Wrong navigation (10%)
  • Scroll/search (12%)
  • Control confusion (7%)
  Total: 44% of failures occur here

PHASE 3: TASK COMPLETION (Steps 8-10)
Failures:
  • Dialog confirmation (14%)
  • Step budget exhaustion (9%)
  • Recovery failures (5%)
  Total: 28% of failures occur here


ACTIONABLE INSIGHTS BY TREND
-----------------------------

1. Early-Stage Prevention (36% of failures):
   - Pre-configure apps (skip setup wizards)
   - Grant all permissions before recording memory
   - Start memory recording from app home screen (not Play Store)

2. Mid-Task Navigation (44% of failures):
   - Provide explicit navigation instructions 
     (e.g., "Menu → Your Lists → Allowed tab" not just "go to Allowed")
   - Train LLM on analog control semantics (drag vs tap, clock face 
     coordinates)
   - Add scroll distance/direction hints in memory

3. Completion Assurance (28% of failures):
   - Always include explicit confirmation steps in memory ("tap OK to save")
   - Increase step budget to 15-20 for multi-dialog tasks
   - Add recovery prompts ("if error, try alternative approach")


SUCCESS CORRELATION
-------------------

High-fidelity runs (≥90%) share these traits:
  • ≤ 5 memory steps (bakerspercentagecalculator SRV: 5 steps)
  • No setup screens (bloodpressuremonitor SRV: started in Statistics view)
  • Direct UI interactions only (taps, text entry, no scrolling)
  • Pre-configured app state (batterytemperaturedisplay HHV: 90% despite 
    permission step)

Low-fidelity runs (<30%) share these traits:
  • Setup wizard present (homeraudioplayer: 0%)
  • ≥ 7 memory steps (homeraudioplayer HHV: 9 steps)
  • Complex controls (luxalarm SRV: analog clock, 11%)
  • Multiple confirmation dialogs (binaryeye: settings navigation, 30-35%)

================================================================================
CONCLUSION
================================================================================

Setup/configuration overhead is the #1 killer (18% of failures), followed by 
analog control semantics (15%) and missing confirmations (14%). Combined, 
these 3 categories account for 47% of all step failures. 

Eliminating setup screens alone could improve average reproduction from 42% 
to ~52%.
