ViBR Workflow Guide

A simple explanation of how src_ViBR works, what goes in, what happens in the middle, and what files come out. This page is based on the current code in src_ViBR and the saved run outputs under apps/<app_name>/llm/ViBR.

Big Picture Workflow Inputs / Process / Outputs Important Functions Output Layout Notes

Big Picture

ViBR tries to replay a bug-report video on a real Android device, one scene at a time.

Input

Recorded Bug Video

ViBR reads a handheld or screen-recorded video and treats it as a sequence of user interaction scenes.

Reasoning

State Matching + Action Inference

It compares the recorded frames with the current device screen, asks an LLM what matters, and predicts the next action.

Output

Replay Attempt on Device

It executes the predicted action through ADB and saves logs and step-by-step artifacts for inspection.

End-to-End Workflow

A readable view of the pipeline from config file to replayed device actions.

1

Read Config

src_ViBR/main.py loads config.yml, checks the settings, and expands shortcuts like hhv or srv into real video file paths.

2

Create Run Folder

It detects whether the video is handheld or screen-recorded, creates a new run directory, prepares logging, and stores metadata for that run.

3

Launch Replay Worker

main.py starts approach/segment_replay.py, passing the video path, segmentation algorithm, output folder, cache folder, and LLM settings.

4

Connect to Device

The replay worker uses ADB to take a live screenshot and dump the current Android UI XML from the device.

5

Read Video Frames

All video frames are loaded. If the algorithm is SSIM, luminance-only frames are also prepared for frame-to-frame similarity checks.

6

Split Into Stable Scenes

ViBR segments the video into stable scenes using either CLIP similarity or SSIM similarity, so each scene roughly represents one user action.

7

Prepare One Scene

For each scene, ViBR saves the recorded start frame, the recorded end frame, and a fresh live screenshot from the device into that step's artifact folder.

8

Parse Current Screen

The UI XML is converted into screen elements. ViBR labels the current screenshot with numbered boxes so the model can point to live targets.

9

Find Relevant Regions

GroundingDINO detects likely interactive regions on the recorded start frame. The LLM then chooses which of those regions best explain the transition to the stop frame.

10

Check State Consistency

The LLM compares the recorded state and the current live state and decides whether the same user action can still be performed from the live screen.

11

Recover or Execute

If the states do not match, ViBR tries up to 3 recovery actions to align the device. If the states do match, it predicts the actual next action and executes it through ADB.

12

Save Evidence

Each step stores intermediate images such as tmp_start.png, dino.png, relevant_regions.png, and labeled.png. The run also stores a log and metadata.json.

Inputs, Process, Outputs

The same pipeline explained as a clean input → process → output flow.

Inputs
  • src_ViBR/input/config.yml for the run list, LLM, model, algorithm, and logging level.
  • A bug-report video such as apps/<app>/videos/handheld/hhv-001.mp4 or apps/<app>/videos/screenrec/srv-001.mp4.
  • A connected Android device available through ADB.
  • GroundingDINO installation and weights.
  • API credentials for OpenAI or Gemini, depending on the provider in the config.
Main Process
  • Read and validate config.
  • Create a run folder and log file.
  • Read the bug video into frames.
  • Split the video into stable scenes.
  • For each scene, compare recorded frames with the live device screen.
  • Use XML + GroundingDINO + LLM reasoning to pick targets and infer actions.
  • Replay the chosen action on the device through ADB.
Outputs
  • A per-run folder under apps/<app>/llm/....
  • artifacts/ with step-by-step screenshots and annotations.
  • logs/ with a full pipeline trace.
  • metadata.json summarizing app, video, algorithm, runtime, and status.
Per-Step Artifacts
  • tmp_start.png: recorded scene start frame.
  • tmp_stop.png: recorded scene end frame.
  • screenshot-0.png: current live device screen.
  • labeled.png: live screen with numbered XML elements.
  • dino.png: all GroundingDINO detections on the recorded start frame.
  • relevant_regions.png: only the LLM-selected important regions.
config → main.py → segment_replay.py → XML / DINO / LLM / ADB → artifacts + logs + metadata

Important Functions

Key functions explained in a simple input / process / output style.

Function Input Process Output
load_config() YAML config path Validates config values, fills defaults, expands hhv/srv into actual video paths, and creates run configs. Normalized pipeline config object
create_output_layout() Project root, app name, llm, source type, timestamp Chooses the base run directory, next run-XXX id, artifacts path, metadata path, and log file path. Output layout object for one run
read_frames_from_video() Video path Reads every frame from the video and also prepares cropped luminance frames for SSIM. frames and y_frames
segment_with_clip() / segment_with_ssim() Frames plus cache folder Computes similarity between neighboring frames, reuses cached similarity when available, and detects stable scene ranges. List of stable segments
parse_xml_string() Android UI XML Extracts visible elements, filters overlaps/noise, and optionally keeps only clickable elements. List of AndroidElement objects
label_screenshot() Live screenshot + parsed elements Draws purple highlight boxes and numeric labels over the current screen. labeled.png
run_grounding_dino() Recorded start frame Detects likely interactive regions such as buttons, icons, text fields, and list items. Detected region list + annotated image
ask_gpt_for_relevant_regions() Recorded start frame + stop frame Asks the model which detected regions most likely caused the transition and what the likely action type was. JSON with target regions and predicted action
ask_gpt_state_consistency() Reference image + current live image Asks whether the same action can still be performed from the live screen. JSON saying same state yes/no
ask_gpt_for_action_region() Recorded start frame, recorded stop frame, live labeled frame Asks the model what exact action to perform now on the device to recreate the same transition. JSON action such as tap, swipe, input_text, back, wait
execute_actions() Action JSON + device controller Maps abstract actions into concrete ADB commands. Device interaction is executed
ADBDeviceController Coordinates, text, shell commands Runs ADB to take screenshots, dump UI XML, tap, swipe, type, and navigate. Live screenshots, XML, and executed actions

What the Output Folder Contains

A run folder stores the main summary plus one artifact folder per source video.

        tmp_start.png
        tmp_stop.png
        screenshot-0.png
        labeled.png
        dino.png
        relevant_regions.png
      step_1/
      step_2/
      ...
  logs/
    <timestamp>__run-XXX__pipeline__success.log
  metadata.json
metadata.json Short run summary: app name, source type, video path, algorithm, runtime, run id, and final status.
Log file Full pipeline trace showing which segment was processed, what the model predicted, whether recovery was attempted, and whether the action was executed or skipped.
artifacts/ Visual evidence for each step so you can inspect what ViBR saw and why it made a particular decision.

Notes and Caveats

Important details that help avoid confusion when reading the code and existing run folders.

Folder Naming Difference

The current create_output_layout() code builds paths like apps/<app>/llm/ViBR_<llm>/<source>/run-XXX, but many existing saved runs in the repository are still under apps/<app>/llm/ViBR/<source>/run-XXX.

What “Same State” Means

ViBR does not require the live screen to look pixel-perfect. It only asks whether the same user action is still possible from the live screen.

Why Some Steps Are Skipped

If recovery fails after the allowed retries, the current scene is skipped. The run can still finish successfully overall even if some scenes are skipped.

Why Both XML and Vision Are Used

XML helps map the live screen into clickable elements and coordinates. Vision helps compare layouts and interpret the recorded video when exact UI structure differs.
