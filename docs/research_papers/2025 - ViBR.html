🎯 Problem Statement

What problem does ViBR solve?

Automatically reproducing bugs from GUI screen recordings (video-based bug reports) — without requiring touch indicators, pre-built UI transition graphs, or app-specific instrumentation.

Why does it matter?

  • Video-based bug reports grew 15–35% between 2018–2020 on GitHub.
  • Reproducing bugs manually from video is time-consuming and error-prone due to GUI inconsistencies between recording device and replay device (resolution, layout, themes).

Gap in prior work

  • GIFdroid: relies on pixel-level SSIM + pre-built UTG (brittle against layout changes; requires ~1hr Droidbot exploration).
  • V2S: requires visible touch indicators — impractical for user-submitted recordings.
  • LLM approaches: text-only; not applicable to video input.

📹 INPUT: GUI Screen Recording (video) + APK
1
Action Segmentation
CLIP + OCR  ·  Split video into atomic action scenes
▼

Goal

Split the raw video into a sequence of atomic action scenes — each scene corresponds to exactly one user action (tap, scroll, or text input).

Step-by-step

  1. Convert every frame from RGB → YUV; extract the Y-luminance channel to reduce JPEG compression artifacts.
  2. Encode each Y-luminance frame through the CLIP image encoder → high-dimensional embedding.
  3. Compute cosine similarity between consecutive frame embeddings.
  4. Classify scene boundary from the similarity curve:
    • Sharp drop → Tap
    • Gradual rise → Scroll
    • Oscillation + keyboard detected by OCR → Input
  5. OCR checks for substrings "qwert" or "123" to detect on-screen keyboard.

Output

Sequence of scenes: each scene = [frame_start … frame_end] + action type label.

Key models / tools

CLIP YUV Y-channel Cosine Similarity OCR
2
GUI State Comparison
GroundingDINO + GPT-4o  ·  Does the device match the recording?
▼

Goal

For each action scene, determine whether the current device screen is in the same functional state as the recording — even if they look visually different (dark mode, different resolution).

Step A — Interactive Region Detection

Run GroundingDINO (open-vocabulary object detector) on the scene's first frame using generic GUI text prompts:

"button" "text field" "search bar" "layout"

→ Returns candidate bounding boxes for all interactive regions.

Step B — Region of Interest (ROI) Selection

Merge the scene's first frame (before action) and last frame (after action) into a single dual-view composite image. Label each detected region numerically.

Ask GPT-4o: "Which numbered region was interacted with?" → returns an integer index → ROI bounding box.

Step C — State Consistency Check

Show GPT-4o two images side-by-side:

  1. Recording's first frame with ROI highlighted by bounding box.
  2. Current device screenshot (live from ADB).

VLM answers: [YES] = consistent (same functional state) | [NO] = inconsistent (device is in a different state).

Key insight

VLMs can reason about functional equivalence — a dark-mode screen and a light-mode screen with the same button are "consistent" even though pixel-level SSIM would say they're different.

Key models / tools

GroundingDINO GPT-4o (VLM) Dual-view composite prompt ADB screenshot
3
Bug Replay on Device
GPT-4o  ·  Execute actions to reproduce the bug
▼

Goal

Execute the right sequence of actions on the actual Android device to reproduce the bug, adapting when the device's GUI state differs from the recording.

Current GUI Perception

Take an ADB screenshot + UIAutomator XML → DFS traversal of view hierarchy → extract all interactive elements → draw bounding boxes and labels on screenshot → give this annotated image to the VLM.

Action Inference — Two Paths

✅ Consistent State

Device is in the same state as recording.

VLM is shown:
1. Recording first frame (ROI highlighted)
2. Recording last frame (post-action)
3. Current device GUI
4. Action type from segmentation

→ VLM selects element + action primitive (direct replay).

⚠️ Inconsistent State

Device is in a different state from recording.

VLM is shown:
1. Recording first frame (target precondition)
2. Current device GUI

→ VLM infers exploratory action to navigate toward the target state.

Action Space

tap [element] tap [back] scroll [up/down] input [element][value] end (bug reproduced)

Execution loop

Repeat Phase 2 + Phase 3 for each scene until VLM outputs [end].

🧠 LLM Usage

Model: GPT-4o (multimodal VLM)

Used as the core reasoning engine for three distinct tasks:

  • ROI Selection — "Which numbered region was interacted with?" (returns integer)
  • State Consistency Check — "Is this interactive region present on the device?" (returns YES/NO)
  • Action Inference — "Which element should I interact with and how?" (returns action primitive)

Prompting Strategy

  • Region-guided attention prompting: dual-view composite image with labeled candidate regions.
  • Binary state comparison: YES/NO output for reliable parsing via regex.
  • Dynamic action inference: two separate prompt templates depending on whether state is consistent or inconsistent.

👁️ Vision Components

CLIP — Scene Segmentation

Encodes Y-luminance video frames into embeddings; cosine similarity between consecutive frames detects action boundaries. No fine-tuning — zero-shot transfer to GUI domain.

GroundingDINO — Interactive Region Detection

Open-vocabulary object detector: given an image + text prompt, finds bounding boxes for regions matching the text. Used with generic GUI prompts ("button", "text field", etc.) to localize candidate interactive regions — no app-specific training needed.

Architecture: Vision backbone → Language encoder (CLIP-based) → Cross-modal decoder → bounding boxes.

GPT-4o — GUI State Comparison & Action Inference

Multimodal VLM; sees annotated screenshots and reasons about functional equivalence and which UI action to take.

💪 Strengths

  • Functionality-aware GUI comparison — handles dark mode, resolution shifts, toast messages that defeat pixel-level methods.
  • No instrumentation — works on standard screen recordings without touch indicators or pre-built UTGs.
  • Fastest execution among baselines (289.1s vs 346.3s vs 904.3s).
  • First framework to leverage VLMs for reasoning over GUI video recordings — new paradigm for video-based GUI engineering.
  • Region-guided prompting is a coarse-to-fine approach: GroundingDINO narrows the search space, then VLM reasons within it.

⚠️ Limitations

Technical

  • Fails when no semantic GUI correspondence (e.g. Dropbox different folder structure).
  • Masked input fields (PIN, password) — VLM can't see actual input value.
  • Action segmentation struggles with delayed rendering and video ads.

Practical

  • Relies on GPT-4o — API cost, latency, closed-source dependency.
  • Small bug replay dataset (38 recordings after filtering from 75).
  • Action space limited to tap/scroll/input — no complex gestures (pinch, multi-finger).

💡 Key Takeaways

One-line summary

ViBR reproduces bugs from GUI video recordings by segmenting actions using CLIP embeddings, comparing GUI states with region-guided VLM prompting, and adaptively replaying actions using GPT-4o — achieving 73.7% reproducibility without any instrumentation.

Most important insight

Region-guided prompting dramatically outperforms full-screenshot VLM comparison (F1: 0.89 vs 0.73). Focusing VLM attention on the specific interaction region is crucial — holistic full-image reasoning is insufficient for fine-grained GUI state comparison.

Ideas to borrow

  • Y-luminance preprocessing before CLIP encoding to reduce compression noise.
  • Region-of-interest dual-view composite prompting for GUI state comparison.
  • Consistent vs. inconsistent state dual-prompt strategy for adaptive action inference.
  • GroundingDINO with generic GUI category prompts for interactive region detection.

Future work (from authors)

  • Sample intermediate frames within scenes for ambiguous transitions (e.g. PIN masking).
  • Expand action space to multi-touch gestures.
  • Apply ViBR to usability testing, tutorial generation, accessibility evaluation.
  • Evaluate across multiple VLMs (Gemini, Claude, Qwen).
