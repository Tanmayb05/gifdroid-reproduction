What problem does it solve?

Manually reproducing Android bugs from bug reports is tedious. Existing automated tools either:

  • Only handle crash bugs — completely miss non-crash functional bugs
  • Extract individual S2R steps (fragile when reports are incomplete or ambiguous)
  • Give no feedback to the LLM — easily get stuck in infinite action loops
Key insight: 88% of users abandon apps with recurring issues. Manual reproduction by developers is slow, error-prone, and doesn't scale.

0
Input
Whole bug report + APK file
▾

ReBL takes two things as input — nothing more:

  • Whole bug report: The complete natural language text a user filed (title, description, steps, expected vs. actual behavior). No preprocessing. No S2R extraction.
  • APK file: The Android app to test, installed on a real device or emulator.
Input: "When I tap the Share button on a photo, the app crashes immediately." APK: com.example.photoapp-v2.3.apk

Why whole report? Non-crash bug symptoms are described in the report body, not in S2R steps. Extracting only S2Rs loses the oracle for detecting the bug.

1
Instructions Setup One-time
Transform GPT-4 into a bug-reproduction agent
▾

Before any iteration, a comprehensive system-level instruction prompt is built once. It tells GPT-4:

  • Objective: Reproduce the bug symptom AND verify it matches the report description
  • Available actions: click, scroll, set_text, back, restart, sleep, long_click, success, fail
  • Response format: Must output structured action(s) per iteration
  • Termination criteria: Output success when bug is observed, fail when stuck
  • Workflow: Observe current UI → pick the best action → report back
You are a bug reproduction agent. Given a bug report and current app state, suggest the next action(s) to reproduce the bug symptom. Actions: [click, scroll, set_text, back, restart, sleep, long_click, success, fail] Format: action_name [target, ...] Stop when: bug symptom matches report description → output success
ITERATIVE FEEDBACK LOOP — repeat until done or timeout
A
App UI Extraction
Read current device screen state
▾

At each iteration, ReBL captures what's currently on the device screen:

  • Activity name: Identifies which screen the app is on (e.g., MainActivity, SettingsActivity)
  • View hierarchy (XML): Full UI tree from UI Automator2

Widget Grouping Algorithm — instead of dumping raw widgets, ReBL groups them:

  • If a layout is clickable → group it with all its children
  • If a layout is not clickable but has ≥1 clickable child → group them
  • Otherwise → group by structural rule
Raw XML: [Button: "Share"], [ImageView: photo], [FrameLayout clickable: true] ↓ Grouping ↓ Group 1: FrameLayout [ImageView, Button "Share"] Group 2: ... → Cleaner context for LLM, avoids token waste on atomic widgets

Why grouping? Reduces cognitive load on LLM. Grouped widgets provide relational context (e.g., "Share button is part of the photo card") vs. orphaned widget IDs.

B
Build Prompt
Assemble full context + token management
▾

The full prompt sent to GPT-4 is assembled from 4 parts:

[Instructions] + [Bug Report] + [App UI Info] + [Prompt History]
  • Instructions: The one-time system prompt from Step 1
  • Bug Report: Full original text (never extracted, always complete)
  • App UI Info: Current activity + grouped widget hierarchy from Step A
  • Prompt History: All prior LLM responses + feedback from past iterations

Token Limit Management:

  • Tracks cumulative tokens C. If C > L × TH (L=8K, TH=0.7 → threshold=5.6K)
  • Triggers semantic summarization of Prompt History (max 3 times)
  • Summarization preserves crucial actions + decisions while reducing length

If 3 summarizations exceeded → terminate (fail)

C
GPT-4 Action Generation
LLM decides what to do next
▾

GPT-4 receives the full assembled prompt and outputs one or more actions:

Available actions: click [target] — tap a UI element scroll [target, direction] — scroll up/down/left/right set_text [target, text] — type into a field back — press the back button restart — restart the app sleep [duration] — wait N seconds long_click [target] — long-press an element success — bug symptom observed ✓ fail — cannot reproduce ✗ Example output: click [Group1: FrameLayout > Button "Share"] → or a sequence: [click [menu], click [share], set_text [field, "test"]]

Can output a sequence GPT-4 may suggest multiple chained actions per iteration when steps are clearly sequential.

D
Execution on Device
Run actions via UI Automator2 + smart detection
▾

Actions are executed on a real Android device or emulator using UI Automator2.

Two smart detection mechanisms run during execution:

  • Quick-disappearing widget detection: Monitors for transient UI elements like toast messages ("Item saved!") or pop-up dialogs that flash briefly. These are captured and fed back to the LLM as context — otherwise they'd be invisible by the next UI extraction.
  • Repeated sequence detection: If the exact same sequence of actions appears twice in the history, ReBL flags it and reminds the LLM to try a different approach (prevents infinite loops).
Execution: UI Automator2.click(element_id=Group1_Button_Share) → Status: SUCCESS → Toast detected: "Sharing requires permission" ← captured! → New UI state: PermissionDialog appeared
E
Update Prompt History
Feed execution result back to LLM context
▾

After each execution, the result is appended to the Prompt History:

  • The action that was taken
  • Whether it succeeded or failed
  • Any transient widgets seen (toasts, dialogs)
  • Whether a repeated sequence was detected (+ reminder to LLM)
Iteration 3 feedback: Action: click [Button "Share"] Status: SUCCESS Toast observed: "Sharing requires location permission" New screen: PermissionDialog (Allow / Deny) → Next: LLM now sees this dialog and can decide to Allow or Deny

This feedback is why ReBL avoids the loops that plagued AdbGPT — the LLM always knows what happened and why, and can course-correct.

→ Loop back to Step A with updated state.

2
Termination & Output
Success, failure, or timeout
▾

The loop terminates in one of three ways:

  • SUCCESS LLM outputs success — it has matched the observed UI state to the bug symptom described in the report
  • FAIL LLM outputs fail — determines it cannot reproduce the bug
  • TIMEOUT 1-hour wall-clock limit exceeded, OR 3 prompt summarizations used up

Bug oracle for non-crash bugs: The LLM compares the current UI state (content, layout, values) against the symptom described in the bug report — no hard-coded crash detector needed. This is what enables non-crash bug handling.

LLM output: success [The photo sharing dialog shows incorrect contact list, matching the bug report symptom "wrong contacts shown"]

How ReBL Prompts GPT-4

Prompt Structure (per iteration)

[INSTRUCTIONS — one-time setup] You are a bug reproduction agent for Android apps. Objective: Reproduce the bug symptom AND verify it matches the description. Available actions: click, scroll, set_text, back, restart, sleep, long_click, success, fail Format: action_name [target, optional_args] Terminate with: success (bug observed) or fail (cannot reproduce) [BUG REPORT — full text, every iteration] Title: App crashes when sharing a photo Steps: Open app → select a photo → tap Share Expected: Share sheet appears Actual: App crashes with "NullPointerException" [APP UI INFO — current screen state] Activity: com.example.app.PhotoViewActivity UI Groups: Group 1: FrameLayout [ImageView (photo), Button "Share", Button "Edit"] Group 2: ToolBar [Button "Back", TextView "My Photos"] [PROMPT HISTORY — prior iterations] Iteration 1: Action: click [Group2: Button "Back"] → FAILED (already on photo view) Feedback: Repeated action detected, try a different approach Iteration 2: Action: click [Group1: Button "Share"] → SUCCESS Toast seen: "Sharing..." New screen: ShareActivity [LLM RESPONSE] → Based on above context, LLM picks next action...

Key Prompting Decisions

  • No few-shot examples — relies entirely on GPT-4's instruction-following ability
  • Whole bug report every iteration — ensures LLM never loses sight of the goal
  • Structured action format — reduces hallucination of invalid actions
  • Feedback in history — distinguishes successful vs. failed actions
  • Explicit termination actions — success and fail are first-class actions, not implicit

Token Management

As iterations accumulate, the prompt grows. ReBL handles this with:

  • Token counter tracks cumulative C
  • Threshold: C > L × TH = 8000 × 0.7 = 5,600 tokens
  • When exceeded: semantic summarization of Prompt History
  • Summarization preserves key actions, decisions, failures
  • Max 3 summarizations — after that, terminates with fail
Trade-off: Summarization risks losing critical earlier context. This is one of the tool's known limitations — some bugs fail because early navigation steps get compressed away.
Failure Cases

1. Third-Party Service Dependencies

Bugs that require Google Drive, payment APIs, or external login services cannot be reproduced — ReBL has no way to authenticate or interact with systems outside the app.

Example: "File uploads fail when backing up to Google Drive" — requires signed-in Google account with Drive access.

2. Extremely Insufficient Bug Reports

When the bug report gives almost no information (e.g., "app doesn't work"), the LLM has no anchor for what to reproduce. The whole-report strategy helps, but there's nothing to work with if the report is empty.

3. Missing Navigation Steps

Some bugs require navigating to an obscure part of the app. If the LLM explores the wrong path and the prompt history fills up, it may never find the right screen before summarization loses critical context.

Technical Limitations
  • GPT-4 only — weaker LLMs (GPT-3.5, smaller models) perform significantly worse. The reasoning capability of GPT-4 is load-bearing.
  • Android only — relies on UI Automator2. No iOS or web support.
  • 1-hour time limit — bugs requiring long exploration chains may not reproduce in time.
  • LLM-based oracle — for non-crash bugs, the LLM decides if the bug is reproduced. This can hallucinate false positives or miss true reproduction.
  • Specific input formats — when a field requires a URL, phone number, or credential, GPT-4 often generates syntactically wrong values.
Open Research Questions
  • How do you handle bugs where the visual symptom can't be described in text? (e.g., layout misalignment, rendering glitches)
  • Can you replace the LLM oracle with a more reliable non-crash bug detector?
  • Can ReBL be extended to iOS or web (Playwright/Selenium)?
  • How does performance degrade with cheaper LLMs for cost reduction?
Connection to next work: ReBL is the text ceiling — it's the best you can do with text alone. ViBR (2025) adds a vision component to handle bugs where visual confirmation is needed.
